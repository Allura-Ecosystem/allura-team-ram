# BMAD Sprint Planning

Generate a `sprint-status.yaml` file by parsing epic definition files, extracting stories, and building a structured status tracker. Never downgrades an existing status.

## Activation

When the user requests sprint planning, status generation, or epic-to-yaml sync, run this skill sequentially. Halt at checkpoints marked **[CHECKPOINT]** for user confirmation.

## Inputs

| Input | Source | Default |
|-------|--------|---------|
| Planning artifacts directory | User or project config | `docs/` then `_bmad/bmm/` |
| Implementation artifacts directory | User or project config | `stories/` |
| Existing `sprint-status.yaml` | Implementation artifacts dir | (may not exist) |

## Step 1: Locate Epic Files

Search for epic definitions in this order:

1. **Sharded layout**: `{planning_dir}/epics/index.md` plus individual `epic-1.md`, `epic-2.md`, etc.
2. **Single-file layout**: `{planning_dir}/epics.md` or any file matching `epic*.md` in the planning dir.
3. **Fallback**: scan `{planning_dir}/` recursively for files containing `## Epic` headers.

If no epics are found, report clearly and halt.

**[CHECKPOINT]** — Confirm discovered epic files with the user before parsing.

## Step 2: Parse Epic Files

Extract structure from markdown headers:

### Epic Detection
- Pattern: `## Epic {num}:` or `## Epic {num} —` or `## Epic {num} -`
- Extract: epic number (integer), epic title (text after the colon/dash)
- Key format: `epic-{num}` (e.g., `epic-1`, `epic-2`)

### Story Detection
- Pattern: `### Story {epic}.{story}:` or `### Story {epic}.{story} —`
- Extract: epic number, story number, story title
- Key format: `{epic}-{story}-{title-kebab}` where title is lowercased, spaces/special chars replaced with hyphens, truncated to 40 chars
- Example: `### Story 1.2: Trace Middleware Integration` → `1-2-trace-middleware-integration`

### Title to Kebab-Case Rules
1. Lowercase the full title
2. Replace spaces, underscores, and non-alphanumeric chars (except hyphens) with `-`
3. Collapse consecutive hyphens to one
4. Strip leading/trailing hyphens
5. Truncate to 40 characters at a word boundary

## Step 3: Build Sprint Status Structure

For each epic, create three categories of entries:

### Epic Entry
```yaml
epic-{num}:
  status: backlog
  title: "{Epic Title}"
```

### Story Entries
```yaml
{epic}-{story}-{title-kebab}:
  status: backlog
  title: "Story {epic}.{story}: {Story Title}"
  epic: epic-{num}
```

### Retrospective Entry
```yaml
epic-{num}-retrospective:
  status: optional
  title: "Epic {num} Retrospective"
  epic: epic-{num}
```

## Step 4: Smart Status Detection

Apply status upgrades (never downgrades) in this order:

### 4a. Story File Check
For each story key, check if a corresponding file exists in the implementation artifacts directory:
- Look for: `{stories_dir}/{story-key}.md`, `{stories_dir}/story-{epic}-{story}.md`, or any file whose name contains the story key
- If found: upgrade status from `backlog` to `ready-for-dev`

### 4b. Preserve Existing Progress
If an existing `sprint-status.yaml` is found:
1. Parse it
2. For each key that exists in both old and new: keep the MORE advanced status
3. For keys only in old file: preserve them (they may be manual additions)
4. For keys only in new file: use the computed status

### Status State Machines

**Epic statuses** (ordered):
```
backlog → in-progress → done
```
An epic auto-upgrades to `in-progress` if any of its stories are `in-progress` or `review`.
An epic auto-upgrades to `done` only if ALL its stories are `done`.

**Story statuses** (ordered):
```
backlog → ready-for-dev → in-progress → review → done
```

**Retrospective statuses**:
```
optional ↔ done
```

### Legacy Status Mapping
If the existing file contains legacy statuses, map them:
- `drafted` → `ready-for-dev`
- `contexted` → `in-progress`
- `complete` → `done`
- `blocked` → preserve as `blocked` (non-standard but valid)

### Never-Downgrade Rule
Compare old and new status by their position in the state machine. Always keep whichever is further along. This is the most critical invariant of this skill.

## Step 5: Generate sprint-status.yaml

Write the output file to `{implementation_dir}/sprint-status.yaml`.

### Output Format

```yaml
# Sprint Status — auto-generated by bmad-sprint-planning
# Last updated: {ISO 8601 timestamp}
# Source: {planning artifacts path}
# Epics: {count}  Stories: {count}  Retrospectives: {count}

development_status:
  # === Epic 1: {Title} ===
  epic-1:
    status: backlog
    title: "Epic 1 Title"

  1-1-story-title-here:
    status: backlog
    title: "Story 1.1: Story Title Here"
    epic: epic-1

  1-2-another-story:
    status: ready-for-dev
    title: "Story 1.2: Another Story"
    epic: epic-1

  epic-1-retrospective:
    status: optional
    title: "Epic 1 Retrospective"
    epic: epic-1

  # === Epic 2: {Title} ===
  epic-2:
    status: backlog
    title: "Epic 2 Title"
  # ... stories ...
```

### Ordering Rules
1. Epics in numeric order
2. Within each epic: epic entry first, then stories in numeric order, then retrospective last
3. Comment separators between epic groups

## Step 6: Validate and Report

After generation, validate:
- Every story references a valid epic
- No duplicate keys
- All statuses are valid per state machines
- Epic statuses are consistent with their stories
